# Configuration review and recovery

Save and apply opens a review of the differences between the current configuration and the draft. Keep editing closes the review without applying. Ordinary traffic edits activate immediately after validation and transaction preparation.

Changing management IP, port, HTTP/HTTPS, management TLS identity, or managed Linux networking starts a **120-second connectivity confirmation**. The header turns yellow and shows Awaiting connectivity confirmation. Open the new management address, verify management and traffic access, then click Confirm configuration. Confirmation must come through the new address and protocol. Revert now restores the preceding configuration immediately; an unconfirmed change restores it automatically at the deadline. Restoring records another revision rather than erasing history.

Only one change can await confirmation. Further applies, certificate inventory changes, HA traffic synchronization, update activation, backup capture and restore staging wait until that change is confirmed or reverted. This protects the objects needed to restore the previous configuration. The warning describes applied but unconfirmed configuration; the draft indicator separately describes edits that have not been applied.

RiverLB writes a private, durable `<database>.confirmation.json` journal with the previous and trial configurations before activation, and records exact firewall rules before changing them. After a process crash or restart it reconciles Linux addresses, VLANs, routes and firewall permissions before restoring the database and creating listeners. Recovery also handles interrupted provisioning before the trial database commit and retries interrupted recovery. An HA node restores only its standby network until cluster authority grants floating ownership. Foreign same-name VLANs are preserved and startup fails with the journal intact for console investigation. Confirmation removes the journal only after the confirmation audit is recorded. Startup refuses unexpected revision conflicts. An explicit successful offline backup restore clears an obsolete confirmation journal afterward.

With `--external-network`, RiverLB saves network object definitions but does not provision Linux or its firewall; definition-only network changes therefore do not start a network confirmation. Management changes still require confirmation. For managed networking, destination-scoped firewalld rules follow the current listener configuration, and rollback restores the previous rules.

If the old management address is unavailable after a rejected or failed network rollback, use console access and examine the logged error and kernel configuration. Recovery cannot replace missing external PEM files, undo an administrator's unrelated OS changes, or repair a failed storage device. Preserve external TLS files separately from database backups.

The API uses `POST /api/v1/config/preview` with `{revision, config}`; `GET /api/v1/config/confirmation` reports the deadline; and `POST /api/v1/config/confirm` or `/revert` accepts `{revision}`. Normal authorization and management request protection apply. `tests/confirmation.py` exercises review, confirmation, mutation guards, manual rollback, crash recovery, the actual fixed deadline, and traffic continuity using disposable state and loopback sockets. `tests/confirmation_network.py` tests committed and precommit crashes, interrupted recovery and foreign VLAN refusal against real Linux objects inside a disposable network namespace.
