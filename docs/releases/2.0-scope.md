# RiverLB 2.0 scope and readiness plan

**Status: proposed; scope, support claims and thresholds await approval.**
Prepared October 21, 2026 for [tracker #8](https://github.com/codyasmith8118/RiverLB/issues/8),
the [2.0 project](https://github.com/users/codyasmith8118/projects/1) and milestone
[2.0.0](https://github.com/codyasmith8118/RiverLB/milestone/1). This plan organizes
work and decisions; it does not certify a production release or approve a date.

## Current baseline

Development integrates into `release-2.0`. Issue #9 is implemented there through
[PR #74](https://github.com/codyasmith8118/RiverLB/pull/74), merge
`033d10bb75f8ec28dc81b05db2052b2cd6e8427e`. Its retained-input, two-build,
disconnected-install and CI evidence applies to the recorded source/artifacts.
It does not establish guest boot, platform fencing, performance or soak results.

The backlog has 65 child issues: 20 P0, 21 P1, 16 P2 and eight P3. As of this
planning audit, only #9 is closed: **1/65 implementation items, 1/20 P0 gates**.
Issue closure is development progress; final release sign-off still requires
qualification of one final artifact set. GitHub issues/project state supersede
this dated snapshot.

Repository inspection found **zero registered self-hosted Actions runners and
zero repository environments**. The disk workflow names `riverlb-kvm` and
`appliance-build`, but those names do not prove provisioned or protected capacity.
Organization-level infrastructure and current access to external labs were not
verified. The [October 13 deployed-lab record](../../tests/lab/deployed-ha-lab.md)
is historical configuration evidence; current availability, ownership and safe
reset/fencing permission require confirmation. No lab endpoints were probed.

## Proposed delivery boundary

1. Require all 20 P0 gates and their dependency closure. That closure also
   includes **P1 #22**, because required networking qualification #23 depends on
   its explicit firewall/listener policy. Proposed minimum scope is therefore
   **21 child issues**, not just the 20 labeled P0. Priority and release scope
   are separate decisions; this proposal does not silently relabel #22.
2. Treat the remaining **36 P1/P2 items** as proposed additions. Accept an item
   only with an owner, complete dependency closure, acceptance tests and lab
   capacity. Otherwise record an approved deferral and adjust milestone/project
   scope and support claims together. No exclusions are approved by this plan.
3. Keep the **eight P3 Discovery items** outside promised shipped functionality
   until a bounded design is approved. Proposed implementation deferral is
   explicit below; a design investigation cannot satisfy production acceptance.
4. Retain the existing capability baseline: TCP full proxy, generic UDP,
   HTTP/1, client/server TLS, WebSocket/SSE, local administration, active/standby
   ownership with fencing, and signed standalone application updates. Every
   advertised capability still needs qualification. HTTP/2/gRPC, mTLS, transparent
   forwarding, live session mirroring, active/active, HA rolling updates and OS
   rollback are not baseline promises. Accepting their issues changes this scope.

## Acceptance and evidence gates

The detailed procedures live in the [qualification plan](../appliance-test-plan.md).
These are proposed approval targets, not recorded successful runs.

| Gate | Proposed acceptance | Owning issues / evidence |
|---|---|---|
| Correctness / security | All mandatory accepted-scope cases pass; no unresolved critical/high defects; invalid trust/auth/update inputs rejected | #14/#16/#17/#18/#19/#25 and final exact-commit CI/security |
| Installation / networking | Every approved firmware/device/topology cell passes clean/existing-disk install, recovery, uniqueness, firewall and SELinux checks | #12/#22/#23; actual guests and interface evidence |
| HA safety | Exactly one traffic owner; verified exclusion/fencing precedes takeover; unavailable fencing safely refuses unsafe takeover | #13/#24; correlated logs and ownership captures from both appliances |
| HA recovery | Proposed controlled move <10 s to five consecutive successful fresh requests; fault budget set from actual detection/fencing timers | #24/#36; count established-session losses separately; safety cannot be traded for a timing target |
| Functional traffic | Zero unexpected transport/TLS/status/payload failures in stable windows; intentional fault windows and expected losses reported separately | #25; per-case backend and client results |
| Distribution / apply | 300 sequential equal-weight requests give 100 per member; weighted 1:2:3 with >=6,000 requests within proposed 5% relative tolerance; metadata-only apply p95 <2 s on approved reference | #25/#36; record concurrency, persistence and topology |
| Capacity / regression | Three matched runs per point; investigate >10% throughput loss or >20% p99 increase against an approved baseline; no universal Gbit/s/CPS promise | #36; generator calibration, raw counters and hardware/tool versions |
| Soak | 24 h at 50% measured sustainable capacity, then final 72 h; no crash/unexplained errors or sustained memory/FD growth after warmup | #37; baseline capacity must be approved first |
| Recovery / migration | Valid encrypted restore and compatible 1.0.1 migration; interrupted/tampered/replayed updates fail or recover as specified | #29/#30/#31; exact versions and durable-state verification |
| Delivery / promotion | Consistent final source, version, update sequence, hashes, SBOM/licenses/provenance and passing qualification; protected authorized signing | #9/#11/#32; preserve publisher-key custody and publish one reviewed artifact set |

Each case records test ID, expected/actual result, source commit and dirty state,
artifact/input hashes, platform/device/tool versions, operator and UTC time,
redacted evidence, defect and retest. Use
[qualification-results.csv](../../tests/lab/qualification-results.csv) as the
execution ledger. Missing/failed/unrun required evidence blocks sign-off; an
approved scope exclusion changes the matrix rather than turning a failed test
into a pass. Preserve summaries/identity/decisions durably; define raw-log
retention and credential/overlay exclusions under #10/#32 before running the lab.

## Development and release workflow

1. Branch each child from current `release-2.0`; target that branch in its PR.
   Record the issue, dependency state and applicable tests. Preserve `main` until
   the complete release is approved. Keep issue #8 open as the parent tracker.
2. Merge implementation only after applicable CI/security and review. Mark a
   child Done with evidence; implementation completion alone does not approve a
   platform or the final release. Requalify when relevant source/inputs change.
3. Freeze an accepted-scope release candidate on `release-2.0`; define the exact
   product version, update sequence and immutable input set under #31/#32.
   Do not rename 1.0.1 artifacts or treat earlier candidate evidence as final.
4. Run the approved matrix and soak on that candidate. Resolve critical/high
   defects; fixes invalidate affected evidence and require documented retests.
5. Review every #8 sign-off row, scope decision and residual limitation. Complete
   #32's protected promotion and open the whole-release PR from `release-2.0` to
   `main`. Approval and one consistent qualified artifact set precede promotion.
